# The maintenance instruments — what each one is, and when to reach for it

This is about the *kinds* of instrument this repository runs, not any one of them.
Which gate catches what is README's gate table and `tools/lib/gates.mjs`.

Documentation here is read on every run by an agent with no memory of yesterday, so a
stale sentence acts like a wrong variable. Keep counts and lists in generated files, and
let prose point at them.

| | answers | fails when | costs |
|---|---|---|---|
| **Gate** | "is this artefact still well-formed?" | an invariant breaks | seconds per run |
| **Hook** | nothing — it makes a gate unskippable | the gate it wraps fails | patience, if slow or noisy |
| **Test** | "does this code do the right thing on known input?" | behaviour changes | maintenance of fixtures |
| **Reference capture** | "how far has upstream moved since we looked?" | drift becomes visible | committed files, re-captured on purpose |
| **State file** | "what is true right now?" | prose disagrees with it | a generator script |
| **CI** | "does it still pass where nobody can skip it?" | any of the above fails | minutes per push |

They fail in different directions and are not interchangeable. A gate does not fix stale
prose.

---

## 1. Gates

**What it is.** A program that answers one question about an artefact on disk and exits
non-zero when the answer is wrong. `check-classes.mjs` asks whether every `rux--*` in the
markup resolves to compiled CSS, and nothing else.

**When to add one.** When a defect could recur silently, and the question that would
catch it can be answered mechanically from files in the repository. A defect that
announces itself needs no gate; a question that needs a human eye cannot have one.

**When not to.**

- **If it needs a growing allow-list, it is not ready.** A rule that reads "everything
  except these 40 cases" measures the 40 cases, and adding an entry is the cheapest way
  to turn it green.
- **If it would be half a check.** A half-version reads as coverage nobody has.

**A gate declares its own blind spots.** Every tool in `tools/` names, in its header,
what it cannot see, because "check passed" otherwise reads as "thing is correct".
`blindTo` and `blindSpots` in the registry are copied from those headers, and are `null`
where a tool states nothing.

**A gate never run against a target is indistinguishable from one that passed.** Point
every gate at every kind of page it applies to, templates included.

**Where they live.** `tools/check-*.mjs` read files and run in `npm run verify`;
`tools/check-*.js` run in a browser against a served page. The registry holds the count.
Read `verify`'s **exit code**: a pipe returns the last command's status and can report a
pass over a failure.

## 2. Hooks

**What it is.** Not a check. A delivery mechanism that makes a check unskippable at a
moment when skipping is tempting.

**This repository has one:** `.githooks/pre-commit`. `AGENTS.md` says what it runs and
how to arm it.

**When to add one.** When the thing guarded is unrecoverable or expensive to undo, and
the check is fast. A hook that is slow or fires falsely gets bypassed, and once the bypass
is known every hook loses its force. Rule of thumb: under about 200 ms and a false-positive
rate near zero.

---

## 3. Tests

**What it is.** A gate checks an invariant over an artefact; a test checks the behaviour
of code against known input.

**The two kinds worth having first:**

- **Conservation tests.** Count what goes in, count what comes out, and fail on any
  category that produces zero. This catches silent omission: code that handles the cases
  it thought of and drops the rest without an error.
- **Golden or snapshot tests.** Commit the rendered output and diff a refactor against
  it. Where a change is meant to be invisible, this proves it.

---

## 4. Reference captures

**What it is.** A committed record of the exact upstream state a claim is made against,
so drift is visible. `docs/carbon-*.json` holds captured Carbon stories that match the
installed Carbon, need no network, and are diffed by `tools/diff-fragment.mjs`.

**When to add one.** Whenever correctness depends on something outside the repository:
a library's DOM, an API's shape. Without one, "we match upstream" means "we matched it
at some unrecorded moment".

**A capture nothing reads is a comment.** Pair it with a gate, or at least a documented
command.

**A `BEHAVIOUR:` comment on a template records a running page:** the URL, the date, the
properties compared and what was not covered. `check-provenance` enforces it, because the
stylesheet records mechanism and says nothing about intent. `docs/verifying-templates.md`
is the procedure.

---

## 5. The state file

**What it is.** One small generated file holding the volatile facts — counts, lists,
ratios — regenerated by a script, committed so `git diff` shows it moving, and cited by
prose instead of restated in it. `docs/inventory.json` and `docs/coverage.json` are
this, and the gates that read them keep their numbers honest.

**The rule.** *Generate state, never prose.* An argument is the valuable part of a
document and no generator can write it; a count is not. Put the count in JSON and have
the prose point at it.

---

## 6. CI

**What it is.** The same gates, run where nobody can skip them. Here it is
`.github/workflows/pages.yml`, which runs `npm run check -- --full` on every push and
deploys `main` only when it passes.

**Two things it does:**

- **It tests the Node floor, not the development version.** `node-version: '22'` matches
  the bound in `package.json` engines.
- **It fails when committed build output is stale.** The check regenerates what is
  committed but derived; a dirty tree afterwards means a source was edited and the old
  output committed.

The gates are listed once, in `package.json`'s `verify` script, and CI runs that. A
second list in the workflow would be a second thing to drift.

---

## Two traps specific to working with an agent

**An agent optimises for the check turning green, not for the invariant holding.** Make
satisfying a check honestly cheaper than gaming it. Where that is impossible, the check
is not ready: record what the attempt learned and leave the rule unenforced.

**A decision with no recorded rejected alternative looks open.** An agent will reopen it
every session. `AGENTS.md` and the README record choices already made; the site's
`docs/status.md` lists what is still open.

- **The individual gates.** README's gate table and `tools/lib/gates.mjs`.
- **What no instrument here does.** The screen-reader pass,
